## Findings

1. **P1 — The successful context handshake releases the GPU claim before the child exits.** `run_gpu.py:382` leaves `with claim_lock()` before `worker.wait()`. `runner.py:144–146` creates only `torch.zeros(1)` before announcing readiness; the full acquisition/model allocation follows later. With two concurrent supervisors and a single eligible card, the second supervisor can enter selection while the first child is still initializing. The actual reused selector was exercised with a CPU card fixture (`used_mib=1`, existing compute PID, no loading claim): it selected the card with the reason `lightest sufficient-memory workload; cohosting`. This exposes an allocation race and violates `AGENTS.md:7`, which requires keeping the claim until the owned child has exited. Retain a claim recognized by subsequent selection for the complete child lifetime, including timeout/interrupt cleanup. The author's correction for failed context initialization is present but does not cover the successful context path.

2. **P2 — SIGTERM bypasses cleanup and leaves the detached numerical child alive.** `run_gpu.py:369–370` starts the child in a new session; `run_gpu.py:385–388` relies on Python exception/finally handling for cleanup. There is no SIGTERM handler. Importing the actual module leaves `signal.getsignal(signal.SIGTERM) == signal.SIG_DFL`. A pure CPU surrogate using the same `Popen(start_new_session=True)` and `finally: terminate_owned(worker)` pattern was terminated with SIGTERM: the parent exited with code `-15` and its child remained alive. That child was then explicitly cleaned up. A scheduler/user TERM therefore loses the supervisor, timeout and failure evidence while training continues. Route SIGTERM through a controlled exception/stop path, terminate and wait for only the owned process group, and persist failure evidence before exiting.
